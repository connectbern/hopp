# Fork features (chagai's Hopp)

This is a fork of [gethopp/hopp](https://github.com/gethopp/hopp) (AGPL-3.0). It tracks
upstream `main`; everything below is kept as small, separable commits on the branch
`chagai/main`. Rebase or merge upstream regularly and re-check this list afterwards.

| # | Feature / fix | Where | Default | Status |
|---|---------------|-------|---------|--------|
| 1 | **Setting: "Show overlay on my screen while sharing"** (Settings → Call settings → Screen share settings). While sharing, Hopp shows an always-on-top transparent overlay window on the sharer's screen that draws a 4 px purple frame around the shared area plus teammates' cursors, drawings and click animations. **Off = that overlay window is never shown while sharing** (it is only used for the screen picker), so no frame, no fill, no title bar can appear; remote control keeps working. Persisted as `share_overlay_enabled` in `app_state.json`, forwarded to `hopp_core` over the socket (`SetShareOverlayEnabled`), applied immediately to an active share. | `tauri/src-tauri/src/{app_state,main}.rs`, `tauri/src/core_payloads.ts`, `tauri/src/windows/settings/main.tsx`, `core/socket_lib/src/lib.rs`, `core/src/lib.rs`, `core/src/window_manager.rs`, `core/src/graphics/graphics_context.rs` | on (= upstream behaviour) | needs a check on Windows after each upstream merge |
| 2 | **Fix (Windows): no title-bar strip across the top of the screen while sharing.** The undecorated, transparent overlay window (and the drawing window) got a classic caption bar painted into their top rows by `DefWindowProc` on activation changes (upstream issue [#277](https://github.com/gethopp/hopp/issues/277); mechanism described in winit [#4733](https://github.com/rust-windowing/winit/issues/4733) / [#4771](https://github.com/rust-windowing/winit/pull/4771)). A window subclass now answers `WM_NCPAINT` / `WM_NCACTIVATE` so the frame is never painted. Matters for the picker phase and for feature 1 = on. | `core/src/window/frameless.rs`, hooked in `core/src/window_manager.rs` and `core/src/window/drawing_window.rs` | always on (bug fix) | drop once upstream/winit ship an equivalent fix |
| 4 | **Fix (Windows): remote typing of punctuation and AltGr characters.** The key map only scanned key codes 0..127, but Windows punctuation keys (`, ; : . - ' `` ` `` etc., VK_OEM_*) are 0xBA..0xE2, so they logged `failed to get keycode for key: ,` and Ctrl/Alt shortcuts on them were lost. Now 0..255 on Windows; the map is built from a clean keyboard state with `ToUnicodeEx(.., flag 0x4, foreground layout)` (no stale Ctrl/Caps Lock, no dead-key side effects); the Alt pass is built as AltGr (with a plain-key fallback for Alt+letter shortcuts); a viewer's `AltGraph` presses Right Alt (extended key); a Unicode key-down now gets a Unicode key-up. | `core/src/input/keyboard.rs`, `core/src/input/keyboard_windows.rs` | always on (bug fix) | offer upstream |
| 5 | **Diagnostics (Windows): lid and screen on/off in hopp.log.** `display_power: lid CLOSED/OPEN`, `display_power: screen OFF/ON` (power-setting callbacks, no window needed), and `remote click ... while the screen is OFF`. Explains "the share froze when I closed the lid": with the screen off Windows stops composing, capture repeats the last picture without any error. | `core/src/utils/display_power_windows.rs`, `core/src/main.rs`, `core/src/input/mouse.rs`, `core/Cargo.toml` (windows features) | always on | keep until the lid question is settled |
| 6 | **Remote commands: an allow-listed teammate drives this Hopp from a web page.** From `https://<server>/remote-control` (plain page served by the backend, works in any browser, the teammate needs no special Hopp build) a trusted person can: start/stop this user's screen share with no click on this machine, make this app join a room / join the caller's current call / leave, and restart the app. Status (online, in a call, sharing) is shown live. **Safety:** off by default; switched on in Settings → Remote access together with a per-teammate allow-list; the list is mirrored to the backend, which refuses everybody else (`403`, same team required, sender taken from the JWT), and the app checks its local list again for every command (`authorize_remote_command`); every command is logged in `hopp.log` (`remote_commands: ACCEPTED/REFUSED ...`) and in the backend log (`remote-control: SENT/RESULT/DENIED ...`); every accepted command raises a system notification and a toast; a remotely started share keeps a banner with a Stop button in the main window. A remote join always starts with mic and camera off. A remote share uses the display shared last in this session, else the primary one, and remote control (mouse/keyboard) follows the existing "Enable remote control by default" setting, exactly like a share started from the picker. **Protocol (additive):** backend → app websocket message `remote_command {command_id, command: status\|start_share\|stop_share\|join\|leave\|restart, from_user_id, from_name, room_id?, issued_at}`, app → backend `remote_command_result {command_id, ok, message, status}`; REST `GET/PUT /api/auth/remote-control/settings`, `GET /api/auth/remote-control/targets`, `POST /api/auth/remote-control/:userId/command`; core socket message `StartDefaultScreenShare`; new table `remote_control_settings` (AutoMigrate, nothing existing is altered). Upstream apps ignore the websocket message; upstream backends answer the new routes with 404 and the app carries on. | backend: `internal/handlers/remoteControl.go`, `internal/models/remotecontrol.go`, `internal/messages/messages.go`, `internal/handlers/websocketHandlers.go`, `internal/server/server.go`, `web/static/remote-control.html`, `test/integration/remote_control_test.go` · app: `tauri/src/lib/remote-commands.tsx`, `tauri/src/lib/fork-build.ts`, `tauri/src/windows/settings/remote-access.tsx`, `tauri/src/windows/settings/main.tsx`, `tauri/src/windows/main-window/app.tsx`, `tauri/src/core_payloads.ts`, `tauri/src-tauri/src/{app_state,main}.rs` · core: `core/socket_lib/src/lib.rs`, `core/src/lib.rs` | **off** | needs a check on Windows after each upstream merge; needs the fork backend image (#7) |

## Upgrading to a new upstream release

1. `git fetch upstream && git merge upstream/main` on `chagai/main` (conflicts, if any, are
   confined to the files listed above).
2. Run the **Build Windows installer (fork)** workflow on `chagai/main`.
3. Install the new `hopp_<version>_x64-setup.exe` over the old one (settings are kept).
4. Verify: share a screen → nothing drawn on the sharer's screen with the switch off; with it
   on, the purple frame but no white strip at the top.
5. Backend: `cd backend && go test -tags integration ./...` (the remote-command tests are in
   `test/integration/remote_control_test.go`), rebuild the image with `Dockerfile.fork` on top of
   the new upstream image, start it against a scratch database first, then swap.
6. Bump `FORK_BUILD_LABEL` in `tauri/src/lib/fork-build.ts` (shown in Settings → Remote access and
   on the control page) and use the same label in the installer file name.
7. Remote commands: with the switch on and a teammate ticked, the teammate's control page shows
   this app as online; Join → Start screen share → Stop → Leave → Restart all answer, each one
   raises a notification here, and `hopp.log` has one `remote_commands:` line per command.
